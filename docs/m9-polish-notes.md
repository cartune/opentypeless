# M9 — 第二輪真機回饋（2026-10-08 下午）

分支 `m9-polish`（疊在 `m8-feedback` 上）。

## 1. 通話中「辨識不到語音」— 已重現、已找到原因、已修（真實通話待驗證）

**根因**：使用者回報用的是內建麥克風、看到 Typelazy 的琥珀色提示、對方聽得到。本機用一個以「語音處理模式」（AVAudioEngine `setVoiceProcessingEnabled`，FaceTime / 電話就是這樣開麥克風）佔住麥克風的小程式重現：

| 情境 | 我們原本的開法（cpal / 一般 HAL） | 語音處理模式開法 |
|---|---|---|
| 沒有通話，喇叭放測試音 | 峰值 −15 dBFS，voiced 66 | −27 dBFS |
| 模擬通話中，喇叭放測試音 | **−38 ～ −60 dBFS，voiced 0**（裝置變 3 聲道） | −21 dBFS |
| 模擬通話中，只有環境音 | −43 ～ −73 dBFS | 有訊號 |

一旦有語音處理工作階段佔住內建麥克風，macOS 給一般 HAL 客戶端的是幾近靜音的串流；但第二個語音處理客戶端能拿到完整的處理後人聲。使用者 04:47–04:49 的三筆 `Recording diagnostics`（我測試時正佔著麥克風）就是這個症狀：`48000Hz/3ch … voiced=0 peak=-40dBFS`。

**修法**（`audio/vpio.rs`、`audio/coreaudio.rs`、`capture.rs`）：
- 開錄前讀 CoreAudio `kAudioDevicePropertyDeviceIsRunningSomewhere`（閒置時為 false、通話時 true，已驗證）。
- 設定 > 語音辨識 > 「通話中的麥克風」：自動共用（預設）/ 一律用通話模式 / 不共用。
- 自動模式下若麥克風已被別的程式使用，就改用 AVAudioEngine 語音處理模式開麥克風（單聲道 48 kHz，經原本的重採樣/降噪/分塊流程），診斷行會記 `mode=vpio`；否則維持 `mode=hal`。
- 整合測試（`cargo test capture_real_mic -- --ignored --nocapture`）：閒置 `mode=hal voiced=66 peak=-9.8`；模擬通話中 `mode=vpio peak=-25.6`（測試音來自喇叭會被回音消除，voiced 偏低；真人聲不會被消除）。
- 第二個語音處理客戶端加入時，通話方的收音沒有變差（−42 vs −45 dBFS，環境音波動內）。
- 未驗證：真實 FaceTime / iPhone 通話。請通話中聽寫一次，把日誌最後一行 `Recording diagnostics:` 貼過來，應該要看到 `mode=vpio` 且 `voiced` 不是 0。

**低層 AudioUnit 的死路**（留作紀錄）：直接用 `kAudioUnitSubType_VoiceProcessingIO`（coreaudio-rs）開，單聲道格式拿到的訊號比 AVAudioEngine 低 15–25 dB，要 9 聲道交錯格式則回呼幾次後停住；原因不明，改走 AVAudioEngine（objc2-avf-audio）後正常。

舊的診斷與保護（保留）：

- **日誌落地**：之前 tracing 只印到 stdout，從 Finder 啟動就全部消失。現在同時寫到
  `~/Library/Logs/com.cartune.opentypeless/typelazy.log.<日期>`（每日輪替）。啟動時記錄版本。
- **每次錄音結束一行診斷**（`Recording diagnostics: device="…" 48000Hz/1ch ns=false duck=true chunks=312 voiced=180 peak=-18.2dBFS`）：
  輸入裝置名稱、取樣率/聲道、是否降噪、是否有壓低音量、總 chunk 數、有聲 chunk 數、整段最大音量。
  靜音門檻是 `voiced < 10`（200 ms）。下次通話時再出現問題，把這行貼給我就能判斷是「麥克風根本沒聲音」還是「門檻太嚴」。
- **ducking 耳機保護**：當預設輸出裝置和預設輸入裝置是同一個（AirPods、藍牙耳機 HFP 模式都是），不再動它的音量，並記 log。
  理由：通話把那個裝置佔住時，再去寫它的音量屬性是多一個干擾來源；而且耳機的麥克風本來就收不到對方的聲音，壓不壓意義不大。
  這**不是**確認過的修法，只是移除一個變數。
- 沒動靜音門檻：在沒看到通話時的 peak dBFS 之前亂改，會把 M1 擋掉的「靜音上傳 → 幻覺字幕」問題再放回來。

請回報：通話時用的是哪個麥克風/喇叭（AirPods？內建？），以及「辨識不到語音」是 Typelazy 的琥珀色提示/「未聽到語音」，還是對方說聽不到你。

## 2. 玻璃膠囊的「黑黑一層」

- 那層是我們自己的 CSS（錄音狀態 `rgba(18,18,22,0.3)` 深色底），不是系統玻璃。已拿掉，改用文字陰影和稍亮的邊框維持可讀性。
- 原生樣式改成 `NSGlassEffectViewStyle::Clear`（完全透出桌面），`opaque(false)`。
- 新增 設定 > 一般 > 進階 > 玻璃樣式：透明 / 一般。Apple 自己的建議是 Clear 在亮色背景上要加一層暗色，如果你的桌布太亮看不清楚，切到「一般」。

## 3. Siri 風格波形

- 後端每 20 ms chunk 用 Goertzel 算 5 個頻帶（150 / 400 / 1000 / 2500 / 5000 Hz）的能量，和總音量一起以 `audio:meter` 送到前端（原本的 `audio:volume` 保留，無聲提示不受影響）。沒有配置記憶體，和降噪一樣在音訊執行緒內安全。
- 前端改用 canvas 畫 4 層上下鏡射的螢光波（青、桃紅、萊姆綠、紫），每層有半透明填色、發光描邊，主層再加一條細白芯讓它在透明玻璃上、亮桌面也看得到。低頻帶推第一層（母音、音高）、中頻帶推第二層、高頻帶推第三層（子音、氣音）、總音量推第四層；相位速度跟著能量變快。靜音時全部攤平成一條細線（誠實，不假動）。
- **靈敏度（第二輪回饋「要很大聲才有波形」）**：日誌顯示一般講話峰值只有 −17…−29 dBFS，每 20 ms 的 RMS 約 −35 dBFS，在後端 −60..0 dB 的量表上只有 0.4 左右；原本前端又把每層再乘一次音量，等於二次衰減，單一 Goertzel 頻帶的絕對 dB 更低，所以波形幾乎不動。修法全在前端 `waveformLevels.ts`，後端量表與無聲提示的門檻不動：
  1. 「說話視窗」：量表 0.2..0.65（約 −48..−21 dBFS）映射到 0..1，再開 0.7 次方，一般音量就落在上半段。
  2. 自動增益：追蹤最近最大音節（每幀衰減 0.994，約 2 秒），把波形除以 max(峰值, 0.55)；小聲講也能撐滿，但靜音和房間噪音不會被放大。
  3. 頻帶只決定「形狀」（各頻帶除以最大頻帶），整體大小由總音量決定，所以不管小聲大聲，母音與氣音都會推不同層。
  - 測試：`waveformLevels.test.ts` 用實測的一般講話量表（level 0.4）驗證主層至少 0.6、主層振幅至少 9 px；靜音仍會歸零；一聲大吼後峰值會衰減，不會把後面的小聲講話壓扁。
  - 疊加方式從 `lighter` 改回一般混合：四層相加在亮桌面會糊成一團白。
- 沒有 canvas（測試環境）或系統開了「減少動態效果」時退回原本的長條。
